# e-Gov 法令カタログ拡張設計

## 背景

現在の対応法令は `LawCode` enum に定義された固定リストで管理されている。法令本文の取得先はすでに e-Gov 法令 API v2 だが、アプリ内の識別子、設定、DB 変換、通知対象、一覧表示が `LawCode` に依存しているため、プリセット外の法令を追加できない。

この設計では、既存の法令をプリセットとして扱いながら、e-Gov の法令一覧または検索結果から任意の法令を追加できるようにする。既存ユーザーのキャッシュ、ブックマーク、通知設定は壊さずに移行する。

## 方針

アプリ内の正規識別子を `LawCode.name` から e-Gov の `lawId` に移す。現在の `LawCode` enum は固定対応法令の本体ではなく、プリセット法令の種データとして扱う。

推奨案は、互換レイヤー付きで段階的に `lawId` 化する案である。`LawCode` と動的法令を並列に扱う案は一時的には小さく見えるが、Repository、通知、ブックマーク、画面遷移に分岐が残り続けるため採用しない。既存データを破棄して作り直す案は、ブックマークや通知対象を失うため採用しない。

## ドメインモデル

新しい法令モデルを追加する。

- `LawId`: e-Gov の `law_id` を表す値。内部表現は `String`。
- `Law`: `id`, `displayName`, `lawNum`, `category`, `isPreset`, `isAdded` などを持つ法令情報。
- `PresetLaw`: 現在の `LawCode` 相当のプリセット定義。既存 enum 名から `lawId` へ変換できる互換マップを持つ。

`Article`、`StructureHeading`、`LawMetadata` の参照は `LawCode` ではなく `LawId` を使う。画面で法令名が必要な場合は、`LawCatalogRepository` から `Law` を引く。

## データ保存

Room に追加法令を保存する `laws` テーブルを追加する。プリセット法令はアプリ内定義から供給し、ユーザーが追加した法令だけを `laws` に保存する。

既存テーブルの `lawCode` カラムは、スキーマ変更の影響を抑えるため当面カラム名を維持し、中身を `LawCode.name` から `lawId` に移行する。コード上では `lawCode` という名前を段階的に `lawId` へ改名する。

移行対象のテーブルは次の通り。

- `articles.lawCode`
- `bookmarks.lawCode`
- `law_metadata.lawCode`
- `structure_headings.lawCode`

DataStore の `enabled_law_codes` は、キー名は互換性のため初回実装では維持し、中身を `lawId` の集合へ移す。読み込み時に legacy enum 名を検出したら `PresetLaw` の互換マップで `lawId` に変換し、変換後の値を書き戻す。

## e-Gov 連携

`EGovLawApiClient` に法令一覧検索 API を追加する。

- `/laws`: e-Gov で公開される法令一覧を取得する。
- `/keyword`: 法令名や法令番号から検索する。
- `/law_data/{lawId}`: 既存の本文取得処理を継続利用する。
- `/law_revisions/{lawId}`: 既存の改正情報取得処理を継続利用する。

e-Gov API v2 の JSON 形式は一部試行版として扱われるため、レスポンスの任意項目は nullable とし、一覧検索のパース失敗は画面全体の失敗ではなく検索失敗として扱う。

## 追加フロー

追加元によって通知対象への反映を変える。

- 法令一覧タブから追加した場合: 法令をアプリの閲覧対象に追加するだけで、通知対象にはしない。
- 設定画面から追加した場合: 法令を閲覧対象に追加し、同時に通知対象にも追加する。

この違いを Repository API に明示する。

- `addLaw(law, enableNotification = false)`
- `addLawFromSettings(law)` または `addLaw(law, enableNotification = true)`

画面側の意図が読み取れるよう、呼び出し元では boolean の意味が埋もれない名前を使う。

## 画面

法令一覧タブでは、現在のプリセット一覧に加えて、追加済み法令を表示する。検索欄は既存のキャッシュ済み条文検索に加え、e-Gov 法令検索へ切り替えられる導線を追加する。検索結果の法令は、追加済みなら通常表示、未追加なら追加アクションを表示する。

設定画面では、通知対象のチェックリストを「プリセット」と「追加した法令」に分ける。設定画面から法令を追加した場合は、その場でチェック済みにする。

削除は初回実装では「追加した法令を一覧から外す」までを対象にする。ブックマーク済みまたはキャッシュ済みの条文データを消すかどうかは別機能として扱う。

## キャッシュ更新と通知

通知対象は `enabledLawIds` を正とする。通知ワーカーは有効な `lawId` の集合からランダムに法令を選び、DB にキャッシュがなければ e-Gov から取得する。

キャッシュ更新ワーカーは、プリセット法令と追加済み法令のうち、メタデータの更新時刻が古いものを対象にする。追加済みだが通知対象ではない法令も、一覧で開いたときには通常通りオンデマンドで取得する。

## マイグレーション

Room は v9 から v10 へ移行する。移行では、互換マップを使って既存 enum 名を `lawId` に置換する。

変換例:

- `CONSTITUTION` -> `321CONSTITUTION`
- `CIVIL_CODE` -> `129AC0000000089`
- `PENAL_CODE` -> `140AC0000000045`

未知の値は削除せず、そのまま残す。これにより、途中バージョンや将来の形式を誤って壊さない。domain 変換側は未知の `lawId` でも、`laws` テーブルまたは e-Gov から法令情報を補完できるようにする。

DataStore は Room migration と独立して、`ApplicationSettingsRepository` の読み込み時に legacy 値を変換する。変換が発生した場合のみ DataStore に書き戻す。

## エラー処理

e-Gov 検索に失敗した場合は、既存のプリセットと追加済み法令の表示は維持し、検索結果だけエラー表示にする。法令本文の取得に失敗した場合は、対象法令の展開または通知生成だけを失敗させ、他の法令には影響させない。

マイグレーション中に未知の legacy 値が見つかった場合は削除しない。ログには英語で記録し、ユーザーのデータを保護する。

## テスト

主に次を確認する。

- `PresetLaw` の legacy enum 名から `lawId` への変換。
- Room v9 -> v10 migration で `articles`、`bookmarks`、`law_metadata`、`structure_headings` が変換されること。
- DataStore の legacy `enabled_law_codes` が `lawId` に変換され、既存のデフォルト六法が維持されること。
- 法令一覧タブから追加した法令は通知対象にならないこと。
- 設定画面から追加した法令は通知対象になること。
- `LawJsonParser` が `lawId` ベースの `Article` を生成できること。
- プリセット外の法令をキャッシュし、検索、通知、ブックマーク参照に使えること。

## 実装順

1. `LawId`、`Law`、`PresetLaw` と互換変換を追加する。
2. `Article`、`StructureHeading`、Repository IF を `lawId` ベースへ移す。
3. Room の `laws` テーブルと v10 migration を追加する。
4. DataStore の legacy 変換と `enabledLawIds` 化を追加する。
5. `EGovLawApiClient` に法令一覧検索を追加する。
6. 法令一覧タブに e-Gov からの追加導線を実装する。
7. 設定画面に通知対象として追加する導線を実装する。
8. 通知、キャッシュ更新、ブックマーク、画面遷移を `lawId` で通す。
9. migration と主要ユースケースのテストを追加する。
